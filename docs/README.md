# 棋逢小鲸

当前源码版本：**v1.14.0**。本次变更见 [版本更新](版本更新.md)。

棋逢小鲸是一个本地运行的 15×15 五子棋程序。黑方先行，不设禁手，连续五子及以上获胜。正式引擎使用纯 Python、纯算法实现，已移除我方神经网络代码、模型加载与训练入口，正常对弈不需要联网、Torch 或 NumPy；桌面界面使用 Python 标准库 tkinter。

本 README 面向使用者和集成者，说明入口、运行方式和能力边界。候选生成、温度搜索、叶子评分、五态判定和缓存续推的完整设计见 [算法设计文档](算法设计文档.md)。协作规则和长期不变量见 [AGENTS.md](../AGENTS.md)。

## 项目入口

| 入口 | 用途 | 说明 |
|---|---|---|
| `play.py` | 桌面图形界面 | 人机、人人、逐步机机、棋谱复盘和搜索树调试 |
| `play_cli.py` | 命令行对弈 | 玩家执黑、AI 执白的交互模式 |
| `gomoku.cli.vs_mode` | 自动机机对弈 | 保存棋谱，适合本地观察和批量运行 |
| `gomoku.protocol` | Gomocup/Piskvork 管道协议 | 由管理器驱动，与外部引擎对战 |
| `gomoku.tools.match` | 自建对战台 | 驱动两个协议引擎并记录结果 |
| `android/` | Android 客户端 | 通过 Chaquopy 运行同一套纯算法引擎 |
| `gomoku.tools.loss_book` | 败局回归库 | 收录、定位和复测旧败局 |

源码版本和已发布 EXE、APK、macOS 包是两个边界。源码修改不会自动进入已有下载资产；正式发布资产以 GitHub Release 及其 `SHA256SUMS.txt` 为准。

## 快速上手

本文所有命令均在仓库根目录执行，脚本和数据路径也以仓库根目录为起点。

本机开发和测试使用 Python 3.14。Windows 可直接使用项目约定的解释器：

```powershell
D:\python3.14\python.exe play.py
```

也可以使用当前环境中已经指向 Python 3.14 的 `python` 命令：

```bash
python play.py
python play_cli.py
python -m gomoku.cli.vs_mode --max-moves 60 --out game.json
```

图形界面默认进入人机模式，玩家执黑。当前未发布源码统一使用旗舰配置，移除轻快／标准／认真三档及旧耗时标签；窗口不再单独修改温度。命令行输入 `H8` 或 `8,8` 落子，输入 `u` 悔棋，输入 `q` 退出。AI 思考在后台线程进行，界面仍可刷新；思考期间不接受新的棋盘操作。

每次 AI 落子后，界面和命令行可以显示决策来源、耗时、叶子评估状态和候选结果。候选五态只描述本次有限搜索树，不是全盘穷举证明。

对方VCF或双三防守时，先从各来源防点并集中筛选我方冲四兼防点；有则只用这些点，没有才取各来源防点交集。权重和顺序保持。若按该规则无可行防点，搜索树以“无共同防点”结束，并给出合法败势兜底；该结论仅针对当前候选政策，非全盘穷举。评分公式和正式温度设置未随此规则更改。

## 对弈功能

### 人机和人人

人机模式支持玩家执黑或执白。人人模式由玩家轮流落子，也可以请求 AI 辅助分析；辅助分析只展示候选，不自动落子，不改变棋盘或后续决策。

### 机机

桌面界面可以逐步让当前一方 AI 落子；需要连续完成对局时使用：

```bash
python -m gomoku.cli.vs_mode --max-moves 60 --out game.json
```

### 棋谱和记忆

棋谱复盘可以读取记录目录或 JSON，逐手回放并建立独立试走分支。对局记录、胜负记忆和败局库默认保存在 `~/.gomoku/`，可用 `GOMOKU_HOME` 修改目录。悔棋会同步撤销棋盘、搜索状态和已记账的终局。

### 搜索树调试（桌面源码功能）

在“棋谱复盘”中打开记录目录或JSON，选择棋局和手数，再点“载入当前手到搜索树”；界面切换到同一复盘窗口内的“搜索树”页签，载入原谱当前手或试走分支，不另开调试窗口。同一局面重复载入或切换页签会保留已有调试会话；选择另一手后再载入才重建。点击“搜索当前局面”，可以实时查看按实际执行顺序增长的搜索树。点击节点查看棋盘、候选来源/顺序/权重、行棋方、评分视角、五态、实际扣温和叶子结束原因。支持计算暂停/继续/停止，以及独立的录像播放、逐事件前后、时间轴、分轮跳转、折叠、缩放和JSON导出。手动导出默认打开项目的 `storages/reviews/搜索树导出/`，文件名带时间；EXE运行时相对EXE所在目录建立同名目录，不写入临时解包目录。仍须点击导出并确认保存，不会自动落盘。

搜索树页使用单独的计算进程和临时记忆目录，不改主棋局或全局胜负记忆。首次按着法重建，**不导入主窗口已有缓存**；随后在搜索树页落子，会调用同一套真实换根逻辑并保留自己的树。先搜索，再“落推荐点”，在“当前调试棋盘”走对方应手，然后再次搜索，即可观察旧树复用和叶子续温。只走一手就改为对方搜索，可能因主评分方不同而重建，不能把它称为缓存命中。

旧节点、本轮新节点、当前节点用不同颜色显示。续温显示旧叶子温度、本轮T0、恢复后的有效温度及门槛拦截情况；它沿正式续温公式计算，不假设简单相加。缓存复用/复制明确标记，静态评分探针不画成递归分支。分数与状态视角分开显示；硬态提前返回的部分分不会伪装成完整分。

为防止调试本身拖垮电脑，默认墙钟120秒（包含暂停，0表示不限）、Windows计算进程私有内存512MiB、录像20万事件；限额可以在调试窗口设置。非Windows平台没有私有内存读数，不声称已执行该内存限制。停止/异常/超限只保留已收到的部分录像，计算进程退出后该缓存作废；要继续请重建。显示深度和每帧最多700个节点只限制绘制，不剪搜索树或录像。记录与绘制有额外开销，调试耗时不能直接当正式性能。

当前入口已接入与Windows打包共用的 `play.py`，可用源码启动验证；已有下载的EXE不会自动更新。本文不表示已完成重新打包、人工视觉验收或正式Release。

## 算法概览

正式决策链为：

```text
棋盘
  -> 棋型识别
  -> 战术候选或普通候选
  -> 温度驱动的有限深推
  -> 叶子评分与五态汇总
  -> 状态优先、同档按分排序
```

算法有四个核心层：

| 层 | 作用 |
|---|---|
| 棋型层 | 从横、竖和两条斜线识别成五、活四、冲四、活三和潜力结构 |
| 搜索层 | 维护黑白状态表，优先生成直接战术、防守点和普通候选 |
| 深推层 | 用温度、候选权重、固定4点候选和路径剪枝展开后续变化 |
| 决策层 | 将叶子分和五态分开汇总，优先选择五态更高的候选 |

算法的关键边界如下：

- `reason` 表示候选生成是否命中战术直接取点分支；它不是五态，也不是全盘原始 0-4 扫描；
- 实际成五优先结束；达到根最低三层后，温度耗尽的继续推进还须满足战术免费额度和续推门槛，命中战术档本身不代表可以无限续推；普通打分候选不能借权重 100 免耗温；
- 温度允许在正温度下扣到负数，但不补温、不清欠温；黑白两方使用相同规则；
- `+1/-1` 是本次展开中的硬必胜/硬必败，`+2/-2` 是直接子孙层的软证据，`0` 是本次搜索未确定；
- 叶子分是局面评价，不是胜率；五态排序优先于同档候选分；贡献汇总只是独立报告，不替换正式选棋评分；
- 真实落子后可以沿旧树换根复用局面结果和欠温叶子，但参数、权重、棋型规则或换根不匹配时必须重建；新树冷搜索可在本次分析内复用严格同上下文的完整结果，路径状态独立保留，原加权评分和五态规则不变。
- 当前源码普通候选池最多4点，根层与内部共用五档动态攻防；战术候选默认前8手免费，之后按2/4/8梯度耗温，不设8手延伸上限。战术候选每节点先展开前3点，其余按原顺序保留为pending，真实换根时沿既有机制补推；部分分支未完成时保留score_complete=false，不能用部分搜索冒充完整搜索。

完整公式、状态转换、候选宽度、缓存身份和回滚边界见 [算法设计文档](算法设计文档.md)。

### 五档动态攻防

当前源码保持普通候选总额4点，在五档之间调整：1档0攻4防、2档1攻3防、3档2攻2防、4档3攻1防、5档4攻0防；根层和深推内部使用同一规则，黑白视角互补。初始3档、进度0；主动新造44加100、43加80、33加60、活三加40、冲四加30，满100切档并保留余数，对方制造威胁向相反方向累计。活四和实际成五不计进度。同一威胁多端点不重复计分，复合威胁不叠加其组成线；持续存在的旧威胁不重复累计。只有静态盘面而无历史时从中性档开始，不追补旧积分。

v1.13.0资产使用旧的固定2攻2防规则；安装包版本应以实际Release资产为准，源码更新不会自动替换本地EXE。档位只用于新节点的普通候选分配，模拟路径独立累计并回滚，缓存命中沿用已有中间节点；同盘面不同档位进度的候选/结果缓存隔离，换根核对状态，政策和分值变化使旧搜索身份失效。叶子评分仍用原压力辅助口径，五档机制不改五态规则；普通棋型扣温和当前根深度拨温是本版本另外两项改动。本地有限对战结果不构成官方等级分或确定棋力提升证明。

战术每批仍为3点；扩大为4点尚待独立实验，不与普通候选五档混为一项改动。

战术补推的受控回传验证已覆盖每批3/4点、黑白互换，以及新增硬胜、补齐全败、只改变分数三类场景；未发现这些路径上“子节点已变、父节点未变”。状态、分数、完整性、贡献汇总及调试事件均有对应核对，但不能据此排除所有真实续推问题，也不是实际棋盘杀棋证明。真实换根后，被裁掉的旧祖先属于历史树，不要求随当前搜索更新；每批4点仍只作实例实验配置，尚未成为默认值。

## 开局库

开局库按完整棋盘和行棋方匹配，使用八种旋转和镜像处理对称局面，不做任意平移匹配。“接管”指固定根落点后继续搜索，不跳过后续深推；直接成五和必须堵五始终优先。提前出谱后立即回到正式候选和深推。

当前源码有两级开局数据：

- **整盘前5手稀疏库**（`gomoku/core/opening_book_front.py`）：唯一可用于接管的来源，只作用于双方合计第1-5手（着手前盘面最多4子）。第6手起不再接管，也不会回落到旧库接管。黑一固定H8；白二保留既有的正邻/斜邻选择方式，另外三类白二只用于覆盖对手可能的应手，不构成我方随机开局策略；黑三27条确认候选；白四74条确认分支；黑五429条候选。每个完整盘面保留全部确认候选，并区分“暂定主着”“已评分覆盖”和“待评覆盖”：有人工明确首选时遵守人工决定，否则取同局面、同视角、同口径的已评候选最高分（杀棋优先且步数少者更强），同分按稳定顺序；待评候选只有根推荐，不当作最高分或零分，也不参与选择。
- **人类经典推荐与后续研究线**（`gomoku/core/opening_book_data.py`）：本方第四次落子起，命中的谱点只作为一个普通根候选加入，不改变递归宽度、原始权重或五态排序，不接管落点。

黑五候选按“每组保底前三，其余普通分严格>400或带正杀棋标签”筛选。429条候选在八种旋转/镜像下归并为407条唯一规范候选（5处同形合并、22处同点评分冲突，冲突保留先写并记录来源，不后写覆盖）。查谱数据不提供五态硬证明，也没有做棋力对照。

当前未发布源码中，“接管”只固定落点，不跳过后续搜索：必须堵五、唯一候选和早期谱着都进入同一套深推并保存子树，实际成五才直接结束。谱着及防守点保留原综合候选权重用于排序和路线，不因唯一性改成100；普通扣温独立读取实际落子方的纯棋型分。已有有效缓存优先复用，不重复建树。

当前未发布源码采用旗舰默认：开局冷启动160、中途冷启动120、续温基础信用160；普通步耗温为`200×(1－w_type/100)²＋3`，其中`w_type=TYPE_SCORE[落子方预测子类]/260×100`，在落子前读取；邻近、攻防一体和记忆加分不进入普通耗温。综合候选分仍用于排序、路径权重和剪枝。普通防守点同样按实际落子方棋型计费，无对应棋型基础分时w_type为0、扣温203；F5样例的活三＋1B基础分130对应w_type=50、扣温53。`MIN_SEARCH_PLIES`默认3，启用最低三层保障：从当前搜索根起计双方实际落子数，前三层仍正常扣温并保存欠温，只暂缓温度停止；终局、硬态、剪枝及续推阻断不豁免。同盘面热读不追加层数，换根后按新根计算，不从每个旧叶子再补三层。内部实验可把`MIN_SEARCH_PLIES`设为0关闭。最低三层不保证补齐pending，也不保证被硬态或剪枝提前结束的分支仍有后续应手。真实对手走中已展开分支才能换根复用；没有对应子节点时仍需冷算。战术梯度及每批3点保持；旧叶按当前根距离拨温`64×2^(-深度/4)`，扣除欠温且保留负数，同盘面不重复拨温，不再按旧深度8硬停止或封顶40。未承诺固定单步耗时。Android入口和已发布EXE尚未随本轮Python改动更新。`compute_move`保留查谱阶段的单点列表返回形态，实际决策已统一经过`analyze_turn`；非终局的`part4_result.type`为`searched`，不再用虚拟超高分表示续推结果。

正式数据位于 `gomoku/core/opening_book_front.py`、`gomoku/data/classical_opening_recommendations.json` 和 `gomoku/core/opening_book_data.py`。前5手清单由 `scripts/build_opening_front_book.py` 从本地实验数据生成（`--check` 只校验，`--report PATH` 输出暂定主着汇总表）；正式运行不读取实验目录，不启动教师，不依赖外部引擎或第三方库。原始图谱、外部引擎和模型不进入正式运行路径。

## 协议与对战台

启动协议入口：

```bash
python -m gomoku.protocol
```

协议坐标使用零基 `(X,Y)`，对应核心坐标 `(r,c)=(Y,X)`。协议入口只做命令解析、坐标换算和输出，选点委托核心服务；诊断信息不能写入标准输出。

不传 `--t0` 时保留开局冷启动160、中途冷启动120和续温信用160。显式传入 `--t0 N` 时，三者一起使用N，避免只改续温、冷搜索仍使用默认值。离线调参的显式 `t0` 同样覆盖三者并在作用域结束后恢复。`gomoku.cli.vs_mode` 无参数文件且未传 `--t0` 时使用正式默认；显式参数文件中的 `deep_t0` 作为该方实验温度，`--t0` 优先。

自建对战台示例：

```bash
python -m gomoku.tools.match \
  --black "python -m gomoku.protocol --t0 80" \
  --white "path/to/pbrain-carbon.exe" \
  --openings 1 --parallel 1 --json comparison.json
```

对战比较应固定对手版本、双方配置、均衡开局集、黑白交换和计时设置，并保存逐局记录。胜率、置信区间和 Elo 差只描述本次对手与样本，不代表全局棋力或官方排名。搜索温度不是硬性单手时限，也不是全局节点上限；复杂局面可能超过管理器的比赛限时。

## 败局回归

败局库用于保留旧败局、记录来源和复测历史，不会自动修改正式算法参数。基本流程是：

```text
收录或导入败局
  -> 规则检查或人工指定关键手
  -> 在新版本恢复多个起点复测
  -> 全部起点完成且通过后归档
```

常用命令：

```bash
python -m gomoku.tools.loss_book list
python -m gomoku.tools.loss_book import --json games.json --ai-side a
python -m gomoku.tools.loss_book locate --id 1a2b3c4d
python -m gomoku.tools.loss_book retest --id 1a2b3c4d
python -m gomoku.tools.loss_book show --id 1a2b3c4d
python -m gomoku.tools.loss_book archive
```

规则定位只报告可直接核验的错过成五、漏堵唯一成五等局部事实；可选外部教师只用于离线比较。有限教师变化、单条主变化和“未发现败手”都不能当作全盘证明。预算不足、缓存缺项、超时和旧棋谱用尽必须保留为未完成或失败。

## 发布与依赖边界

正式运行路径保持纯 Python 和标准库能力。我方运行路径没有神经网络开关或模型依赖。外部教师程序及其配套模型仅供显式离线实验，不进入我方正式决策；历史实验快照不作为运行模块。外部对手和教师的选定主副本统一放在本地 `storages/engines/<引擎名>/<版本>/`，程序、模型和配置一起保存，来源及旧路径对照见该目录的 `catalog.json`。

正式发布资产由 GitHub Actions 构建并上传到 Release：Windows EXE、Android debug APK 和 macOS zip。下载资产后必须用同一 Release 的 `SHA256SUMS.txt` 校验；源码更新、本地构建成功或单个平台构建成功，都不等于完整 Release 已更新。

离线调参和教师实验只写入独立实验目录，不自动替换正式参数。实验报告应记录输入局面、源码身份、解释器、搜索设置、开关、预算和停止原因；有限搜索结果不能写成全局证明。
