# 棋逢小鲸 v1.4.2

棋逢小鲸（Gomoku）是一个本地运行的五子棋程序，使用 15×15 棋盘，黑方先行，不设禁手。项目提供图形界面、命令行对战和 AI 自弈功能。正式版本采用纯 Python 算法，不需要联网，也不依赖大模型或神经网络。

## 快速上手

项目核心只使用 Python 标准库。安装 Python 3 后，在项目目录运行：

```bash
# 启动图形界面，推荐首次使用
python play.py

# 启动命令行对战，玩家执黑、AI 执白
python play_cli.py

# 让两个 AI 自动对弈，并把棋谱保存为 game.json
python -m gomoku.cli.vs_mode --max-moves 60 --out game.json
```

图形界面默认进入人机模式，玩家执黑。点击棋盘空位即可落子，AI 会在后台思考并自动应手。

命令行模式支持输入棋盘坐标，例如 `H8`；也可以输入零基行列坐标，例如 `7,7`。输入 `u` 悔棋，输入 `q` 退出。

# 第一部分：对弈界面与功能

## 1. 界面布局

图形界面分为三个区域：

- 左侧是控制区，用于选择对局模式、执子颜色和 AI 棋力，也可以新建对局、悔棋、认输、求和或查看记忆。
- 中间是信息区，用于显示双方落子、AI 思考时间、候选走法和判断结果。
- 右侧是棋盘。棋盘会随窗口大小自动缩放，最后一手棋会用红点标出。

AI 的计算在线程中进行，思考期间窗口仍可正常刷新。为避免状态混乱，AI 思考时不会接受新的棋盘操作。

## 2. 对局模式

### 人机

玩家可以选择执黑先行，也可以选择执白后行。轮到 AI 时，程序会自动计算并落子。

### 人人

黑白双方在同一台电脑上轮流落子，程序负责检查落点、胜负和对局状态。

### 机机

图形界面中的“机机走一步”按钮每次让当前一方 AI 落一手，便于逐步观察计算过程。如果希望两个 AI 连续自动下完一局，可以使用快速上手中的 `vs_mode` 命令。

## 3. 对局操作

- **新对局**：按照当前模式和执子设置重新开始。
- **悔棋**：撤回最近的有效着法，并同步恢复棋盘、AI 内部状态和已经产生的终局结算。
- **认输**：当前应当操作的一方认输，立即结束对局。
- **求和**：将本局按和棋结束。
- **查看记忆**：查看累计战绩、输棋类型和历史棋谱信息。

## 4. AI 棋力

界面提供三个棋力档位。它们使用相同的判断方法，区别主要在于计算深度和用时：

| 档位 | 适合场景 | 特点 |
|---|---|---|
| 轻快 | 快速体验、简单局面 | 响应最快，计算较浅 |
| 标准 | 日常对弈 | 默认档位，兼顾速度和判断深度 |
| 认真 | 复杂中盘、算杀测试 | 计算更深，复杂局面可能等待较久 |

档位越高，AI 越愿意继续计算后续变化。实际用时由局面复杂程度决定，不是固定时间。

## 5. 思考结果

每次 AI 落子后，信息区会显示本次计算耗时和候选走法，通常列出前五个候选。每个候选可能包含：

- 棋盘坐标；
- 综合评分；
- 是否为最终选中的走法；
- 强制链状态：`必胜`、`存在必胜`、`无`、`存在必败`、`必败` 之一。

状态含义：

- `必胜` / `必败`：当前候选根节点的硬结论；
- `存在必胜`：当前层发现过硬必胜子分支，但没有硬败势；
- `存在必败`：当前层发现过硬必败子分支（硬败势优先于硬胜势）；
- `无`：当前层没有发现硬必胜或硬必败证据。

软证据只在当前层有效，不再向父层传播；父层聚合时把 `存在必胜` / `存在必败` 当作“无”处理。

界面不再显示数值胜败比；“没有发现”只表示本次实际展开的搜索树里没有出现相应证据，不代表全盘穷举证明。

“叶子评估：纯算法（N 个叶子）”表示 AI 本次实际评估了多少个搜索末端局面。“叶子未触发”表示这一步可以直接决定，例如立即成五、必须堵五或只有一个合法候选，不需要继续展开。

当前正式界面固定使用纯算法叶子评估和纯算法选点。项目中保留的网络接口属于实验或预留能力，默认关闭，也不属于正式发布内容。

## 6. 对局记忆

独立版默认把对局数据保存在：

```text
~/.gomoku/
├── games.json          进行中的对局
└── global-memory.json  总战绩、输棋类型和胜负棋谱
```

可以通过环境变量 `GOMOKU_HOME` 修改保存目录。对局结束后，程序会记录胜负和棋谱；如果终局后悔棋，原结算会一并撤销，重新结束时再重新记录。

# 第二部分：算法内部逻辑

## 1. 整体流程

AI 每次落子依次经过四个步骤：

```text
识别棋型 → 生成候选点 → 推演后续变化 → 排序并选择落点
```

对应的核心模块是：

```text
pattern → search → deep_search → engine
```

这四个模块共用同一套棋盘状态。图形界面、命令行和插件适配层只负责调用，不会另外实现一套选点规则。

## 2. 棋型识别

程序会检查棋盘上的每个空位，判断某一方落在这里后可能形成什么结构。判断时会观察横、竖和两个斜线方向，并把结果分为 18 个细分类别。为了便于理解，这些类别可以概括为：

| 类别 | 常见情况 | 作用 |
|---|---|---|
| 直接或强制取胜 | 成五、活四、双冲四、三四、双活三 | 优先寻找或防守 |
| 明显威胁 | 冲四、活三及其不同形态 | 用于连续进攻和逼迫应手 |
| 后续潜力 | 眠三、活二等 | 用于普通局面的候选评分 |
| 暂无作用 | 当前不能形成有效棋型 | 通常不会优先考虑 |

黑白双方各有一张棋型状态表。真实落子和模拟落子后，程序只更新可能受影响的区域，不必每次重新扫描整张棋盘。

## 3. 候选点生成

程序不会从所有空位中盲目搜索，而是先按紧急程度筛选候选点：

1. 自己有一步成五的位置，直接取胜；
2. 对方下一步能够成五，优先封堵；
3. 自己存在活四、双冲四、三四等连续进攻机会，进入深度计算；
4. 对方存在上述威胁，生成相应防守点并保留不同防守点的重要程度；
5. 检查双方的双活三等强威胁；
6. 没有明确战术时，综合进攻与防守评分生成普通候选。

普通局面下，程序会根据双方威胁强弱调整进攻和防守的比重。局面落后时更重视防守，局面占优时更重视进攻。历史棋谱也可以对普通候选分作小幅修正，但不会绕过当前局面的战术判断。

## 4. 深度推演

对每个根候选，程序会模拟“自己落一手、对方应一手”，然后继续向后计算。每次模拟落子都会同步更新棋盘和棋型状态；该分支结束后再完整恢复，保证不同候选之间不会互相污染。

深推使用“温度预算”控制计算量。可以把它理解为每一步拥有一笔有限的思考预算：

- 评分高、威胁大的走法消耗预算较少，因此可以继续看得更深；
- 普通或较弱的走法消耗预算较多，因此较早停止；
- 搜索越深，保留的候选会逐步减少，明显较弱的分支也会提前停止。

这种方式把更多时间放在关键攻防和连续杀棋上，同时避免普通局面的分支数量无限增长。界面中的“轻快、标准、认真”就是三种不同的初始预算。

## 5. 搜索末端评分

当某一分支已经分出胜负，或者思考预算耗尽时，程序会对当前结果评分：

- 已经成五时，胜方得到最高等级的结果；
- 尚未结束时，读取当前棋盘上双方每个空点可能形成的棋型；
- 先比较双方是否出现成五、强必杀（活四、双冲四、三四）、弱必杀（双三），出现即按固定分档计；
- 双方都没有必杀时，按全盘威胁分求和，再结合当前攻防倾向修正，最后做平滑压缩。

各分支的结果会按路径重要程度汇总。一路都选择高质量走法的变化影响更大，较弱或较深的变化影响会逐步减小。

这里的“评分”只用于比较候选好坏，不等同于“必胜”。高分候选仍可能没有得到明确的强制胜负结论。

## 6. 必胜、必败与五态判定

强制胜负判断与普通评分分别计算。只有一条取胜路径中，胜方的每一步都持续形成对方必须应对的威胁，这条路径才会成为强制胜负判断的依据。

节点使用 5 个离散状态，硬结论与软证据分开保存：

```text
+1  必胜       硬结论
+2  存在必胜   软证据
 0  无         没有证据
-2  存在必败   软证据
-1  必败       硬结论
```

合并规则：

- 所有子节点都是硬必胜 → 当前节点硬必胜；
- 所有子节点都是硬必败 → 当前节点硬必败；
- 否则，只要任一子节点是硬必败 → 当前节点为存在必败（硬败势优先于硬胜势）；
- 否则，只要任一子节点是硬必胜 → 当前节点为存在必胜；
- 否则为无。

存在必胜 / 存在必败是当前层的局部软证据，只由硬状态 ±1 产生，不再向父层传播；父层聚合时按“无”处理。

这些结论只针对本次实际展开且没有被提前停止的变化，并不是对棋盘上所有可能走法的完整证明。

## 7. 最终选择顺序

所有根候选按状态档位排序，同一档内再比较候选分：

```text
必胜 > 存在必胜 > 无 > 存在必败 > 必败
```

- 只要存在更高档位的候选，就优先选择更高档位；
- 同一档位内按综合评分降序；
- 如果所有候选都落在败势档，先选“存在必败”里分数最高的，再轮到“必败”里分数最高的兜底；
- 如果所有候选都是“存在必败”，界面会提示“全部候选均发现败势分支，局面高危”，但不等于根节点被证明必败。

## 8. 当前能力边界

- 开局和布局主要依靠局部棋型与攻防评分，对全局厚势和空间的理解有限；
- “必胜/存在必胜/存在必败/必败”都只来自本次有限搜索树，不是全盘穷举证明；
- 局面评分基于棋型分类，无法表达所有细微形状差异；
- 状态表使用局部更新，少数远端潜力点可能与整盘重新扫描的结果存在差异；
- 神经网络相关代码属于本地实验或预留能力，不代表当前正式版本正在使用网络。

## 开发与测试

### 主要目录

```text
gomoku/
├── core/           棋型、候选、深推和决策流程
├── adapter/        外部进程与插件适配
├── cli/            命令行和自弈入口
├── tests/          Python 与本地插件回归测试
├── game.py         对局规则与状态
├── session.py      单局会话
├── service.py      AI 落子服务
└── memory.py       战绩与棋谱记忆
android/            Android 客户端（Kotlin + Compose + Chaquopy）
scripts/            引擎同步与发布辅助脚本
play.py             图形界面入口
play_cli.py         命令行入口
```

### 运行测试

```bash
# 完整 Python 回归
python -m unittest discover -s gomoku/tests -v

# 深推、叶子与候选排序定向回归
python -m unittest gomoku.tests.test_leaf_value -v
python -m unittest gomoku.tests.test_deep_sync -v
python -m unittest gomoku.tests.test_rank_candidates -v

# 本地存在插件层和 Node.js 时运行
node --test gomoku/tests/test_plugin.cjs
```

### Android 客户端

`android/` 是 Kotlin + Compose 客户端，通过 Chaquopy 17 在 App 内运行同一套纯算法引擎；当前只产出 debug APK，release 需要配置签名。构建前先在仓库根目录同步内嵌引擎：

```bash
python scripts/sync_android_engine.py
python scripts/sync_android_engine.py --check
```

本地构建需要 JDK 17、Android SDK 和 Python 3.14，详细命令见 `android/README.md`。

### 发布产物

推送 `v*` 标签会触发 `.github/workflows/release.yml`：在 Windows EXE、Android debug APK、macOS zip 三平台全部构建成功后，才会创建并发布 GitHub Release，并附加 `SHA256SUMS.txt`。构建产物不进入源码仓库。

### 可选评估工具

| 工具 | 用途 |
|---|---|
| `gomoku/tools/eval_openings.py` | 用一组中盘局面批量评估不同设置 |
| `gomoku/tools/ga_tune.py` | 自动搜索棋型分值和搜索参数 |
| `gomoku/tools/bench_ga.py`、`verify_ga.py` | 对比并验证参数结果 |

自动调参结果默认不加载。如需启用已有的 GA 参数，可以设置环境变量 `DSH_GOMOKU_GA=1`。
