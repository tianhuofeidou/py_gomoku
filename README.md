# 棋逢小鲸

棋逢小鲸（Gomoku）是一个本地运行的五子棋程序，使用 15×15 棋盘，黑方先行，不设禁手，连续五子及以上获胜。核心引擎使用纯 Python、纯算法实现，正常对弈无需联网或神经网络；桌面图形界面使用标准库 tkinter。

本文介绍当前源码。下载版的版本与功能以对应 GitHub Release 及其源码标签为准；本地尚未发布的工具和修改不会自动进入 EXE、APK 或 macOS 包。

| 入口 | 用途 | 运行边界 |
|---|---|---|
| 桌面 GUI、CLI、自弈 | 人机、人人、逐步机机和自动自弈 | 共用核心引擎，人类开局库与纯算法搜索 |
| Android | 在手机内运行同一套引擎 | Chaquopy 内嵌 Python，当前发布 debug APK |
| Gomocup 协议与对战台 | 由管理器驱动、与外部引擎配对对战 | 外部引擎自行提供；比赛计时与本机搜索预算分开 |
| 败局回归工具 | 收录、定位、从关键节点附近重赛 | 当前源码 CLI；默认规则扫描，可选外部教师离线复盘 |
| 离线调参工具 | 用教师标注拟合手工参数并验收 | 本地开发实验，结果不自动替换正式参数，不随正式程序加载教师 |

阅读入口：[对弈功能](#第一部分对弈界面与功能)、[算法概览](#第二部分算法内部逻辑)、[开发与测试](#开发与测试)、[败局回归](#败局回归库待处理败局--新版本复测)。函数级机制见 [算法设计文档](算法设计文档.md)，开发流程与不变量见 [AGENTS.md](AGENTS.md)。

## 快速上手

源码运行和测试使用 Python 3.14；先确认 `python --version` 指向该解释器，再在项目目录运行以下命令。下载的发布包按对应平台说明启动。

```bash
# 启动图形界面，推荐首次使用
python play.py

# 启动命令行对战，玩家执黑、AI 执白
python play_cli.py

# 让两个 AI 自动对弈，并把棋谱保存为 game.json
python -m gomoku.cli.vs_mode --max-moves 60 --out game.json
```

图形界面默认进入人机模式，玩家执黑。点击棋盘空位即可落子，AI 会在后台思考并自动应手。

命令行模式支持输入棋盘坐标，例如 `H8`；也可以输入从 1 开始的行列坐标，`8,8` 与 `H8` 等价。输入 `u` 悔棋，输入 `q` 退出。

终端里 AI 每走一手都会打印本次决策的来源（`棋谱开局` / `棋谱候选＋纯算法` / `纯算法`）、耗时、叶子评估状态和前五个候选（含五态）。开局谱着的分数显示为 `谱着`，不按必胜直取展示；这些字段都取自本次实际决策结果，命令行入口不另算一套。

# 第一部分：对弈界面与功能

## 1. 界面布局

图形界面分为三个区域：

- 左侧是控制区，用于选择对局模式、执子颜色和 AI 棋力，也可以新建对局、悔棋、认输、求和或查看记忆。
- 中间是信息区，用于显示双方落子、AI 思考时间、候选走法和判断结果。
- 右侧是棋盘。棋盘会随窗口大小自动缩放，最后一手棋会用红点标出。

AI 的计算在线程中进行，思考期间窗口仍可正常刷新。为避免状态混乱，AI 思考时不会接受新的棋盘操作。

## 2. 对局模式

### 人机

玩家可以选择执黑先行，也可以选择执白后行。轮到 AI 时，程序会自动计算并落子。

### 人人

黑白双方在同一台电脑上轮流落子，程序负责检查落点、胜负和对局状态。轮到任意一方时，
可以点击“AI辅助分析”让纯算法引擎分析当前局面；分析只在信息区列出首选点和前五个候选的
评分、五态结果，同时在棋盘上用由亮到暗的黄色编号光圈标出推荐顺序。它不会替玩家落子，
也不会改变棋盘；落子、悔棋或重开后，旧推荐会自动清除。
人机模式同样提供这个按钮，但只在轮到人类时可用——AI 回合的分析等于替 AI 想棋，按钮会置灰。
分析结果仅供玩家参考，不会改变 AI 的选点。
窗口最小尺寸为 900×560，保留控制面板、候选日志和棋盘的显示空间。

### 机机

图形界面中的“机机走一步”按钮每次让当前一方 AI 落一手，便于逐步观察计算过程。如果希望两个 AI 连续自动下完一局，可以使用快速上手中的 `vs_mode` 命令。

## 3. 对局操作

- **新对局**：按照当前模式和执子设置重新开始。
- **悔棋**：撤回最近的有效着法，并同步恢复棋盘、AI 内部状态和已经产生的终局结算。
- **认输**：当前应当操作的一方认输，立即结束对局。
- **求和**：将本局按和棋结束。
- **AI辅助分析**：人人模式双方都能用；人机模式在轮到人类时可用，AI 回合不可用（替 AI 分析没有意义）。后台分析当前行棋方的候选点，不自动落子，也不影响 AI 后续决策。
- **查看记忆**：查看累计战绩、输棋类型和历史棋谱信息。
- **棋谱复盘**：当前源码 GUI 可选择对局记录目录或 JSON 文件，在独立窗口切换棋局、筛选胜负、逐手回放和手动试走。成功载入后会在应用数据目录的 `replay-settings.json` 记住记录目录，下次打开复盘窗口自动载入；目录失效时提示重新选择，选择文件/目录对话框也优先定位上次目录。支持评测 `dataset.json`、败谱 `defeats.json`、对战台 `games` 和单局 `moves`；目录只扫描本层与直接的 `results/` 子目录，有统一数据集时载入 `dataset.json` 及同目录的 `重赛_*.json`，重赛排在列表前面；不重复导入败谱汇总和原始逐局文件。读取错误会提示，不自动修正原谱。备注与分支需另行导出，不写入对局记忆或全局败局库，也不影响正在进行的对局。人工试走不提供五态结论。此功能尚未进入已有 Release EXE，需运行当前源码验证。

源码验证可直接运行 `D:\python3.14\pythonw.exe play.py`（工作目录为仓库根目录）。本机“棋逢小鲸（源码测试）”快捷入口与正式 EXE 入口分开；源码更新无需重新打包。

## 4. AI 棋力

界面提供三个棋力档位。它们使用相同的判断方法，区别主要在于计算深度和用时：

| 档位 | 适合场景 | 特点 |
|---|---|---|
| 轻快 | 快速体验、简单局面 | 响应最快，计算较浅 |
| 标准 | 日常对弈 | 默认档位，兼顾速度和判断深度 |
| 认真 | 复杂中盘、算杀测试 | 计算更深，复杂局面可能等待较久 |

档位越高，AI 越愿意继续计算后续变化。实际用时由局面复杂程度决定，不是固定时间。

## 5. 思考结果

每次 AI 落子后，信息区会显示本次计算耗时和候选走法，通常列出前五个候选。每个候选可能包含：

- 棋盘坐标；
- 综合评分；
- 是否为最终选中的走法；
- 强制链状态：`必胜`、`存在必胜`、`无`、`存在必败`、`必败` 之一。

状态含义：

- `必胜` / `必败`：当前候选根节点的硬结论；
- `存在必胜`：尚未确定胜败，但对手有已知必败应手，可以利用对手的失误；
- `存在必败`：尚未确定胜败，但本方下一手有已知必败落点，需要避免自身失误；
- `无`：本次搜索尚未确定胜败，且没有上述本层证据。

软证据只在当前层有效，不再向父层传播；父层聚合时把 `存在必胜` / `存在必败` 当作“无”处理。

硬结论优先；两种软证据同时出现时显示“存在必败”。软状态不表示失误概率。界面不显示数值胜败比，所有结论均限于本次实际展开的搜索树，不代表全盘穷举证明。

“叶子评估：纯算法（N 个叶子）”表示 AI 本次实际评估了多少个搜索末端局面。“叶子未触发”表示这一步可以直接决定，例如立即成五、必须堵五或只有一个合法候选，不需要继续展开。

当前正式界面固定使用纯算法叶子评估和纯算法选点。项目中保留的网络接口属于实验或预留能力，默认关闭，也不属于正式发布内容。

## 6. 对局记忆

独立版默认把对局数据保存在：

```text
~/.gomoku/
├── games.json           进行中的对局
├── global-memory.json   总战绩、输棋类型和胜负棋谱
├── loss-book.json       待处理败局、来源和复测历史
├── loss-review-reports/ 离线定位报告（自动定位后生成）
└── loss-review-cache/   可选教师缓存（启用教师后生成）
```

可以通过环境变量 `GOMOKU_HOME` 修改保存目录。对局结束后，程序会记录胜负和棋谱；如果终局后悔棋，原结算会一并撤销，重新结束时再重新记录。

# 第二部分：算法内部逻辑

## 1. 整体流程

AI 每次落子依次经过四个步骤：

```text
识别棋型 → 生成候选点 → 推演后续变化 → 排序并选择落点
```

对应的核心模块是：

```text
pattern → search → deep_search → engine
```

这四个模块共用同一套棋盘状态。图形界面、命令行、Android 和插件适配层调用同一核心，不另实现一套选点规则。

人类开局库在入口按完整局面查谱；谱外立即进入上述决策链。对局结束后的败局收录、离线教师复盘和参数拟合各有独立入口，不在每手决策中启动教师或训练。对局记忆可小幅修正普通根候选分，败局库本身不会自动变成开局答案或修改引擎参数。

## 2. 棋型识别

程序会检查棋盘上的每个空位，判断某一方落在这里后可能形成什么结构。判断时会观察横、竖和两个斜线方向，并把结果分为 18 个细分类别。为了便于理解，这些类别可以概括为：

| 类别 | 常见情况 | 作用 |
|---|---|---|
| 直接或强制取胜 | 成五、活四、双冲四、三四、双活三 | 优先寻找或防守 |
| 明显威胁 | 冲四、活三及其不同形态 | 用于连续进攻和逼迫应手 |
| 后续潜力 | 眠三、活二等 | 用于普通局面的候选评分 |
| 暂无作用 | 当前不能形成有效棋型 | 通常不会优先考虑 |

连续五子及以上按成五识别；连续段外隔着空位的同色棋子，不会把已经成五的结果降为带缝眠四。

黑白双方各有一张棋型状态表。真实落子和模拟落子后，程序只刷新受影响的区域，不必每次重新扫描整张棋盘：范围是**落子所在棋段**（以对方棋子或连续三空为界）的段内全部空缝，加上该棋段**两端外侧的空位**。这个范围与整盘重算逐格一致，所以既不需要额外的兜底区域，黑白双方也走完全相同的更新路径。

每个空位还按黑白分别缓存四个方向的档位。一次落子只重算区内各空位与落子共线的方向，其余方向直接复用，再合成原有棋型编号。模拟结束时，方向缓存和状态表通过同一份 journal 一起回滚；悔棋或载入棋盘时全量重建。这项优化减少重复扫描，不改变候选规则、评分、五态判定或搜索参数。

### 人类开局库

开局阶段按**本方已经落过几颗子**判断：本方第 1～3 次落子命中完整盘面的可靠推荐才采用谱着，
不进入温度银行；提前出谱立即交回原算法的候选生成和深推。直接成五和必须堵五仍优先。
执黑对应全盘第 1、3、5 手，执白为第 2、4、6 手。原算法候选池为空时补一个合法点，避免稀疏开局无法落子。
每局从八种旋转/镜像视角中随机抽取一个，仅用于前三手接管。黑方首手为中心时，
白二在正邻、斜邻两类中各占一半机会，八个相邻点等概率选择，不再默认隔一路。
其余局面仍按完整盘面变换应手，不能随意旋转落点。同一局重复分析、实际落子和悔棋保持一致，
新对局重新抽取；局面打破对称后可能只有一个应手，因此不保证每局都走不同位置。

本方第 4 次落子起，命中的谱点只补入普通根候选，与原有候选一起深推。
已有强制攻防候选时不混入谱点；不修改递归宽度、原始权重计算或五态排序。
谱点已在候选中时不重复添加，否则至多增加一个根候选，可能增加该手计算量。
没有命中棋谱就沿原算法选点。谱着本身不产生必胜/必败标签，未展开时显示“无”。

正式数据来自励精连珠教室的人类定式说明及 RenLib 的人类编纂研究树，已替换原 Rapfi 推荐。
明确推荐与未评级研究线分开：只有前者可用于前三手接管；后者仅在本方第四手起补一个根候选，
仍需现有算法评估。树中唯一续着不等于最强着，不能冒充接管推荐。
26 种三手棋形均整理了白四应手，黑五、白六只收录已核对的部分变化，不保证每条路线走满六手。
原始资料使用连珠规则，当前仅参考着法，不导入其禁手胜败结论；也不把研究树或回归通过当成棋力提升证明。
完整盘面与行棋方按八种旋转/镜像匹配，不按着法输入次序、局部形状或平移位置查谱。
正式运行只读取纯数据，不运行外部引擎、不加载模型、不新增第三方依赖。

推荐坐标、采用理由和来源摘要见 `gomoku/data/classical_opening_recommendations.json`；
生成数据及来源校验值见 `gomoku/core/opening_book_data.py`。原始图谱、注释和软件压缩包不入库。
离线复现：`python scripts/import_classical_openings.py --manifest gomoku/data/classical_opening_recommendations.json --library-dir <已下载的lib目录> --output-dir <临时目录>`。
工具检查源文件 SHA256，区分推荐和研究线，不按遍历次序猜最强着；只写指定目录，不自动覆盖正式库。
文本清单的摘要统一按 LF 换行计算，生成文本固定使用 LF；原始 `.lib` 仍按原始字节校验 SHA256。
原 Rapfi 生成脚本保留作独立实验，不是当前正式数据来源。
桌面辅助分析和实际落子显示“棋谱开局”或“棋谱候选＋纯算法”；谱外按实际算法路径显示，叶子统计仍按实际计算显示。

## 3. 候选点生成

程序不会从所有空位中盲目搜索，而是先按紧急程度筛选候选点：

1. 自己有一步成五的位置，直接取胜；
2. 对方下一步能够成五，优先封堵；
3. 自己存在活四、双冲四、三四等连续进攻机会，进入深度计算；
4. 对方存在上述威胁，生成相应防守点并保留不同防守点的重要程度；
5. 检查双方的双活三等强威胁；
6. 没有明确战术时，综合进攻与防守评分生成普通候选。

连续四子的紧邻两端都是盘内空位时识别为活四，端外的隔空棋子不会把它降成冲四；一端封堵和真正的跳四仍按对应棋型处理。

其中第 3 条里，四三（三四）在落子前会先确认一件事：对方被迫堵四的那一手，会不会顺手把自己的四也做成（反四）。会的话，这一步就不再按必杀处理，改由第 4 条及之后的判断决定。原因是四三要三步才能兑现（冲四逼应、活三转活四、补一端成五），只逼得动对手一手；对手那一手若同时成四，先手就换了人。活四、双冲四不受这条影响，它们一步堵不完。

普通局面下，程序会根据双方威胁强弱调整进攻和防守的比重。局面落后时更重视防守，局面占优时更重视进攻。历史棋谱也可以对普通候选分作小幅修正，但不会绕过当前局面的战术判断。

## 4. 深度推演

对每个根候选，程序会模拟“自己落一手、对方应一手”，然后继续向后计算。每次模拟落子都会同步更新棋盘和棋型状态；该分支结束后再完整恢复，保证不同候选之间不会互相污染。

深推使用“温度预算”控制计算量。可以把它理解为每一步拥有一笔有限的思考预算：

- 每步在落子前复用当前攻防优先级：实际选中的必杀候选或对应防守候选免耗温，包括权重为 80 的端点防守（含紧贴威胁点的近端 d=1）；这不直接证明必胜；
- 普通候选按原权重公式扣温。活二落成活三后，更新表可能出现下一手的活四点，但不能追溯让刚才的普通步免费；全盘其他位置有必杀点也不能让无关走法免费；
- 每一手落子前，温度为零或负数时只允许当前零耗温战术候选落子；普通候选即使权重为 100，也仍耗温 3，不能补走。正温度允许本步按原公式扣至负数，之后逐手检查下一方的战术候选；
- 实际成五立即结束；否则，更新棋盘和状态表后，若温度耗尽且下一方不走战术直接取点分支，就在当前盘面评分。双方落子后都能停止，始终按根决策方视角计分，不再补本方普通一步；
- 深推内部普通候选固定 2 攻 1 防、最多 3 个；根层普通候选仍按动态攻防档位取点（含谱点补入），战术候选仍最多 5 个。温度和路径权重继续控制展开，内部普通候选不再按深度逐级收窄。

这种方式把更多计算放在关键攻防上。免耗温战术链仍使用每层最多 5 个候选和路径权重剪枝，不代表完整 VCF/VCT 穷举；普通内部节点固定 2 攻 1 防、最多 3 个候选。连续威胁可能增加节点数和单步用时，普通温度不再限制这部分深度。界面中的“轻快、标准、认真”就是三种不同的初始预算。

深推先用硬状态筛选，再补齐根候选评分：对方已有必胜应手时，本方该分支可提前判败；同一方选择层找到必胜时，也不再为了判态继续展开其他选择。两种软状态和“无”不能用于硬剪枝。

先按原完整路径计算，直到找到一个非必败候选，再对后续候选启用硬态早停；全必败局面不额外先筛选一遍。所有非必败候选仍补齐原始加权分和直接子/孙节点证据；如果全部候选必败，则全部补齐原始分后选兜底。只有存在非必败替代时，已被淘汰且尚未完整评分的必败候选显示“未补算”（`score=null`、`score_complete=false`），不会拿中间累计分参与选择。其余候选 `score_complete=true`。补分复用本次已完整计算的子树和叶子，不从头重复计算；这些派生缓存只在本次固定上下文有效。

需要全部数值分的调用方可用 `analyze_turn(..., complete_scores=True)` 或 `rank_candidates(..., complete_scores=True)` 沿完整评分路径。可选网络和采样同样保留完整路径。Android 当前不显示候选分，独立界面与本地插件会显示“未补算”。每次决策固定入口温度，界面切档从下一手生效。温度仍按路径控制深度，不是新增节点总额度。

正式对弈会保留跨回合树缓存：真实落子命中旧树子节点才换根，未命中、悔棋/重建、参数或权重变化时丢弃旧树；判态/补分临时缓存不跨回合。命中旧欠温末端时按 `T0 + min(0, 旧温度)` 续算，同一局面重复分析不会重复加温。缓存只减少重复计算：同盘面重复分析的加速不等于实战整体提速，也没有新增全局节点上限。

## 5. 搜索末端评分

当某一分支已经分出胜负，或者思考预算耗尽时，程序会对当前结果评分：

- 已经成五时，胜方得到最高等级的结果；
- 尚未结束时，读取当前棋盘上双方每个空点可能形成的棋型；
- 先比较双方是否出现成五、强必杀（活四、双冲四、三四）、弱必杀（双三），出现即按固定分档计；
- 双方都没有必杀时，按全盘威胁分求和，再结合当前攻防倾向修正，最后做平滑压缩。

每个回传层对保留的分支按权重归一化，计算加权均值；候选和对方应手的相对重要程度仍会影响评分，绝对路径权重仍用于剪枝。分叉更多不会直接把分数绝对值累加放大；五态判断独立于数值评分。

续推的战术身份来自下一行棋方候选生成的直接取点分支（`reason`），与叶子分档和五态无关。温度耗尽后只允许零耗温战术着法；普通步不追溯免温，但它在正温度下落完后，下一方若有零耗温战术应手仍可继续。普通步产生的新威胁也可以进入叶子分档估值，不代替实际搜索。这里的“评分”只用于比较候选好坏，不等同于“必胜”。高分候选仍可能没有得到明确的强制胜负结论。

## 6. 必胜、必败与五态判定

胜负状态与普通评分分别计算。实际成五直接提供确定的胜败证据，此前的布局或防守不会使终局证据失效；能否保证取胜，由每层双方的最优选择回传决定。

节点使用 5 个离散状态，硬结论与软证据分开保存：

```text
+1  必胜       硬结论
+2  存在必胜   软证据
 0  无         未确定且没有本层软证据
-2  存在必败   软证据
-1  必败       硬结论
```

每个落子节点描述该步落子方。直接子节点是对手的应手，孙节点是本方下一手：

- 对手有任一硬必胜应手 → 当前节点硬必败；
- 对手所有已展开的有效应手都硬必败 → 当前节点硬必胜；
- 未确定时，本方直接孙节点存在硬必败 → 存在必败；
- 否则，对方直接子节点存在硬必败 → 存在必胜；
- 其余为无。硬结论优先，软证据同时出现时风险优先。

存在必胜 / 存在必败只描述当前候选附近的失误机会或风险，不代表高手对弈下的确定结果。它们上传时按未确定保留分支，不翻转、不删除。风险只读取直接孙节点的硬败，不采集更深层任意败点。
直接成五候选可标必胜；堵五或其他唯一候选若未实际展开，只标无，不能从高分或唯一候选推断胜败。

这些结论只针对本次实际展开且没有被提前停止的变化，并不是对棋盘上所有可能走法的完整证明。

## 7. 最终选择顺序

所有根候选按状态档位排序，同一档内再比较候选分：

```text
必胜 > 存在必胜 > 无 > 存在必败 > 必败
```

- 只要存在更高档位的候选，就优先选择更高档位；
- 同一档位内按综合评分降序；
- 如果所有候选都落在败势档，先选“存在必败”里分数最高的，再轮到“必败”里分数最高的兜底；
- 如果所有候选都是“存在必败”，界面提示本方下一手均有失误风险，尚非确定必败；如果全部必败，则提示本次搜索中按候选分选择兜底。

## 8. 当前能力边界

- 已收录开局可由人类棋谱辅助；出谱后的布局主要依靠局部棋型和攻防评分，对全局厚势和空间的理解有限；
- “必胜/存在必胜/存在必败/必败”都只来自本次有限搜索树，不是全盘穷举证明；
- 局面评分基于棋型分类，无法表达所有细微形状差异；
- 神经网络相关代码属于本地实验或预留能力，不代表当前正式版本正在使用网络；
- 搜索温度不是硬性单步时限，也不是全局节点总额度；复杂局面可能超出管理器的比赛限时；
- 败手定位和旧谱重赛是改进工具，不能替代独立棋力对照，也不证明未发现的局面没有错误。

### 与外部引擎对战（Gomocup / Piskvork 协议）

引擎可以按 Gomocup 的管道协议启动，从而接入 Gomocup 生态（和现成引擎对战、被管理器驱动）：

```bash
# 协议入口：从标准输入读命令、向标准输出回坐标
python -m gomoku.protocol

# 自建对战台：驱动两个协议引擎互相对局（支持均衡开局与黑白互换）
python -m gomoku.tools.match \
    --black "python -m gomoku.protocol --t0 80" \
    --white "path/to/pbrain-carbon.exe" --openings 1 --parallel 1 --json comparison.json
```

- 坐标 0 基，协议里的 `(X, Y)` 对应内核 `(r, c) = (Y, X)`；
- `START` 只接受 15×15，其它尺寸回 `ERROR`（管理器可另试尺寸）；`START/BEGIN/INFO/BOARD/TURN/END/ABOUT` 均已实现；
- `BOARD` 接受乱序棋子，按双方子数确定黑白并交替重建盘面；有序输入保留原顺序，乱序输入无法恢复真实落子历史。非法坐标、重复点、不支持的 field 和不合法子数返回 `ERROR`；
- 每次输出立即 flush，且除协议内容外不向标准输出写任何东西（诊断走 stderr）；
- 可执行文件名必须以 `pbrain-` 开头才会被管理器按管道协议识别；
- `--t0` 用于覆盖推演温度：批量自对弈可降到 40 加速，正式对局保持默认 160。

已知限制：**没有按时间迭代加深**，单手计算由温度和局面决定，不能按 `INFO timeout_turn` 动态收缩搜索预算；超时判定由管理器负责。具体耗时须在指定解释器、局面集和配置下测量，不从档位推断固定响应时间。

自建对战台按每方独立计时：初始化计入本方整局耗时，单步或整局任一正数时限超出即判负。
等待回复的预算取单步上限与本方整局剩余时间的较小值，持续输出 `DEBUG/MESSAGE` 不会重置计时；
超时后结束该局子进程。`START` 也有等待上限（正数单步时限，否则 30 秒，再受整局预算限制），
初始化失败单列为异常局；对战台未模拟 Piskvork 的初始化宽限与计时容差。

`python -m gomoku.tools.review --json <对战记录.json>` 可记录每回合的五态。
“存在必败”仍属非硬必败候选；实际着法不在候选时标为“未评估”，不据此认定败着。
只有实际着法已评估为硬必败且另有非必败候选时才报告该差异，结论仅针对本次搜索树，
“非必败”不保证可守，“全部候选必败”也不代表全盘已被穷举证明。

以下本地打包仅用于协议诊断或开发，不替代正式 Release；需要另行准备与 workflow 相符的构建依赖。管理器可识别的引擎文件名必须以 `pbrain-` 开头，且**必须是控制台程序**：

```bash

  --name "pbrain-QifengXiaojing" \

  --exclude-module torch --exclude-module numpy --exclude-module gomoku.nn \
  --specpath build --workpath build/work --distpath dist \
  pbrain.py
```

```bash
    --black "dist/pbrain-QifengXiaojing.exe" \

```

批量模式会打印 A（`--black` 指定引擎）的胜率、Wilson 95% 置信区间与 Elo 差估计，
并可 `--json` 落盘——这是后续任何棋力改动的验收口径。

批量模式默认使用 `gomoku/data/official_openings.json` 中源自 Piskvork `openings.txt` 的均衡局面，每条让 A 分别执黑、执白各下一局。用于棋力对照时，固定对手版本、双方配置、开局集、颜色配对和计时，保存逐局 JSON，并区分正常胜负、超时与协议异常。这种本地测试不等于参加官方比赛或取得官方排名。

`--opening-set random` 仅作指定种子的开发实验。性能报告需注明 Python 版本、硬件和搜索设置；胜率、区间和 Elo 差仅针对本次对手及样本。测试成绩应附可复核的逐局记录，历史成绩与失效记录见对应实验报告。

### 败局回归库（待处理败局 → 新版本复测）

这部分描述当前源码 CLI，新增教师定位能力需使用包含 `gomoku/tools/loss_review.py` 的源码运行。
收录 AI 输掉的棋局、定位疑似关键败手，引擎更新后从败手附近恢复局面重赛，检查旧问题是否仍存在。

流程为：收录或导入 → 定位或人工指定 → 新版本复测全部起点 → 全部通过后手动归档。定位、复测、归档是不同动作，不会因教师给出好分数就自动移除败局。

**数据位置**：`~/.gomoku/loss-book.json`（可用 `GOMOKU_HOME` 覆盖）。**不写入源码目录，不进 Git。**

败局库 CLI 的标准输出和错误输出使用 UTF-8，包括帮助和导入结果；重定向输出时也按 UTF-8 读取。

**自动收录**：AI 在**人机模式**下正常输棋并完成归档时，`Game._archive_finished` 会自动收录本局（来源记为 `live`），并把来源 id 写进对局历史。**悔棋撤销终局时**（`_rollback_solidify`）会撤销这一条收录——只删该来源，同棋谱的其它失败记录不受影响。
收录失败记在 history 的 `lossBookError` 字段里；撤销失败会向调用方抛出异常，不静默忽略。
外部对战台的结果当前需要显式运行 `import`，不会因生成了对战 JSON 就自动写入败局库。

**导入限定**：`import` 只收 **AI 输**的局；按 `win_by` 将超时、异常与正常棋力失败分开，`list --kind loss` 只看正常失败。对战台的 `winner` 是 `'B'`/`'W'`/`'draw'`/`None` 字符串（不是整数），导入时会先归一化；胜、和、未知一律跳过并计数。

```bash
# 查看待处理败局
python -m gomoku.tools.loss_book list

# 从对战台 JSON 导入失败棋局（--ai-side 指对战台里的哪一方是 AI）
python -m gomoku.tools.loss_book import --json games.json --ai-side a

# 定位疑似关键败手（定位不出时会说明原因）
python -m gomoku.tools.loss_book locate --id 1a2b3c4d

# 定位不出时，人工指定"本方第 N 次落子"
python -m gomoku.tools.loss_book locate --id 1a2b3c4d --ply 12

# 在当前版本上从败手附近重赛（败手 / 前一回合 / 前两回合 三个起点）
python -m gomoku.tools.loss_book retest --id 1a2b3c4d

# 只测"引擎或开局库指纹已变"的案例
python -m gomoku.tools.loss_book retest --stale

# 查看逐局结果
python -m gomoku.tools.loss_book show --id 1a2b3c4d

# 把已通过的案例移入归档（保留原棋谱与复测历史）
python -m gomoku.tools.loss_book archive
```

**定位疑似败手的规则**：默认 `locate` 只扫描规则可核验的 `missed-win`（错过立即成五）和 `missed-block`（漏堵对方唯一立即成五点），不再用“首次硬败前一手”猜败因。实际点即使不在我方候选中也会检查；本方能立即赢优先于防守。对手已拥有两个不同的立即胜点且本方不能立即成五时，只标记已无即时救点，不把最后落点当败因。漏堵是局部战术事实，不证明堵后整盘可守。

可选使用已有 Rapfi 做**离线**教师复盘，不参与正式选棋，不下载或打包教师，也不改变我方纯算法/NN默认开关：

```bash
python -m gomoku.tools.loss_book locate --id 1a2b3c4d --teacher "/path/to/pbrain-rapfi" --cache-dir storages/loss-review --workers 4 --seconds 600
# 只读复用身份匹配的教师缓存，缺项返回未完成，不启动教师
python -m gomoku.tools.loss_book locate --id 1a2b3c4d --teacher "/path/to/pbrain-rapfi" --cache-dir storages/loss-review --cache-only --dry-run --report storages/loss-review/report.json
```

教师分别分析实际/替代落子后的子局面，用相同预算统一换算为败方视角；不能把落子前后分数下跌直接当错棋。默认20万节点粗筛，再对分差较大的至多3个节点用100万/400万节点复核（`--nodes`、`--shortlist`可配置）。连续两档中，同一个替代点均为教师胜线、实际线均被教师判败，才生成 `teacher-win-to-loss` 搜索嫌疑；普通分和“未判败”只保留为待复核证据。保留多次机会，强度相同优先取较晚手，不强造唯一答案；短名单和有限预算可能漏掉更深的机会。

导入时保存预置手数；缺省仅跳过已记录的预置手，无元数据时从第一手检查并提示，可用 `--start-ply N` 明确跳过前N手。自动嫌疑的 `ply` 是**总谱1基手数**，人工 `--ply N` 仍是**本方第N次落子**，不可混用。

原始缓存按教师EXE、配置、权重、规则、节点/时间上限和完整局面身份校验。单进程单线程，最多4并发，共享 `--seconds`/`--max-queries` 预算；独占缓存锁不自动抢占或清除。拒绝非法PV，不把一条合法主变化当全盘证明。CLI保存独立JSON报告和案例 `diagnosis`；`--dry-run` 不写败局库。预算/缓存缺项返回2，协议/输入错误返回1；部分/失败诊断保留旧锚点。分析期间案例更新/删除则拒绝写回；新锚点使旧复测批次失效并退回pending，历史仍保留，定位本身不能令案例通过或归档。

`gomoku/tests/data/loss_locator_annotations.json` 是实现前冻结的人工标注：规则/强制链样例可独立核验，已见的教师辅助实战样例单列为开发对照，不冒充独立准确率。

**五态只描述有限搜索**：`无` 不代表安全，"存在其他未判必败候选"也不证明守得住。定位不出时保留 `undetermined` 原因，允许人工指定手数，不伪造结论。

**复测结果分类**：

| 结果 | 含义 | 能否移出待处理 |
|---|---|---|
| `win` / `draw` | 真实胜局 / 合法终局和棋 | 作为通过结果，仍须整轮起点全部通过 |
| `loss` | 仍失败 | 否 |
| `diverged` | 旧败线改变（旧谱落点已被占），待续测 | 否 |
| `script-exhausted` | 原棋谱用尽但未终局 | 否 |
| `budget-exhausted` | 达到手数上限，**不自动算和棋** | 否 |
| `error` | 异常 / 非法落子 / 超时 | 否 |

**通过条件是「同一轮应测的全部不同起点均完成并通过」**：每次启动复测先保存独立轮次 ID、应测起点和引擎指纹，并把状态设为 `pending`。中断后重新运行会新建一轮，旧轮结果保留作历史，不混入新轮；重复测试同一个起点不能代替未测的起点。任一起点失败或未完成，案例仍留在待处理库；`archive` 只移 `status=passed` 的案例。

默认测试全部起点。`--stop-after-first` 可提前停止，但未测齐时保持 `pending`；只有一个应测起点时，该起点通过即可完成本轮。恰好在手数上限落下的成五或合法满盘和棋先按真实终局记录，不误算为预算耗尽。

**版本筛选看「最近一次复测」**：`retest --stale` 只选「最近一次复测所用的引擎/开局库指纹 ≠ 当前指纹」的案例；已用当前版本测过的不会重复入选。

**边界（明确没做的）**：

- 尚未选定外部陪练引擎，第一版**按原败局棋谱回放对手**；旧谱用尽或落点冲突时如实记为"未完成"，**不编造更弱的对手**；
- **升级后自动后台触发复测尚未实现**，目前只由 `retest` 命令手动启动；
- 「通过原败线回归」只表示**这条旧败线在新版本上不再复现**，**不是**证明全局不败。

### 可选评估工具

以下为源码或本地开发工具，正式对弈不依赖它们。教师训练及运行说明可能尚未包含在已有 Release 或对应标签中；使用前确认当前检出存在所需模块。

| 工具 | 用途 |
|---|---|
| `gomoku/tools/loss_review.py` | 败手定位的规则扫描与可选 Rapfi 教师后端，由败局 CLI 调用 |
| `gomoku/tools/eval_openings.py` | 用一组中盘局面批量评估不同设置 |
| `gomoku/tools/ga_tune.py` | 自动搜索棋型分值和搜索参数 |
| `gomoku/tools/teacher_tune.py` | 实验性教师调参：叶子缓存、交替优化、断点及独立验证 |
| `gomoku/tools/teacher_train.py` | 新版本地训练调度：公共候选评分、训练内留出、完整轮次拟合、多进程和优化器断点 |
| `gomoku/tools/bench_ga.py`、`verify_ga.py` | 对比并验证参数结果 |

自动调参结果默认不加载。如需使用仓库已有的 GA 参数加载路径，可设置环境变量 `DSH_GOMOKU_GA=1`；它不会自动加载教师实验输出的 `best.json`。

离线教师调参使用 Python 3.14 和用户提供的 Rapfi；教师可以使用其自身模型，我方仍拟合手工参数。实验产物可集中保存在已忽略的 `storages/experiments/`，
不改变正式引擎默认值。运行、续跑与配对对战步骤见 [调参运行说明](调参运行说明.md)。
新版训练使用 `python -m gomoku.tools.teacher_train run`；旧版 `teacher_tune run` 保留原有实验口径。
新版训练只支持叶子及候选参数分层优化，教师标注和搜索由隔离进程并行执行；
保留测试集不参与自动训练，参数通过验收后也只供实验协议入口显式加载。
叶子拟合默认固定步长，可显式选择回溯策略，在拒绝更新后恢复已通过约束的参数及Adam状态并缩小步长；
从既有评审参数继续实验时须标记验证集为已见回归，不能继续声称独立验收。
可选`coordinate`策略在缓存树上直接按实际选点质量试探单项叶子权重，保留相同质量与成本约束。
候选评分可选`--score-policy coordinate`：先筛查正式搜索节点，再按新前段权重重建树、
同步扩充公共候选池后比较；默认仍使用随机试参，也可单独指定`--groups score`。
预算有限时可显式用`--score-keys`限制试探轴，轴列表属于断点身份，不能续跑时更换。

可选 `--leaf-policy boundary --leaf-evaluations 1024` 使用有界范围扩展和分界搜索：在原合法参数范围内逐级扩大各轴试探，对训练拟合折上已观察到选点变化的区间继续细化。每阶段固定原点；完整训练集的原质量约束决定保留哪份参数，内部留出折不参与提案生成，外部验证仍在结束时检查。旧 `coordinate` 和默认 `fixed` 保持原策略。

离线搜索固定不叠加本机棋谱记忆，避免未记录的经验分改变候选温度和树结构；正式引擎仍保持原记忆行为。训练搜索与显式实验协议入口共用此作用域，退出后恢复。本次上下文修正会改变实验源码身份，旧树和旧断点不得直接复用，旧参数文件须按新上下文重新验收；身份一致的教师标签仍可只读复用。

`--leaf-evaluations` 限制每阶段候选参数评估尝试数，包含中断前已预留的尝试；重复参数不重复评分，续跑不重置额度。报告记录停止原因、实际完成次数、投影后的变化字段及留出折是否真正改选。预算不足可能未覆盖全部轴；两端选点相同的窄收益窗口也可能漏掉，不能把本阶段结束称为全局收敛。策略、预算或源码变化必须用新目录，历史断点不迁移。boundary 从既有参数续训时，还必须同时改善本轮起点的训练和验证；不通过则 `best.json` 保留起点，`candidate.json` 保留待审结果，不以相对默认值的旧收益推荐新参数。

可选 `--reuse-search-cache <已完成的 teacher_train 实验目录>` 可重复指定，只读复用兼容树和正式搜索探针；教师标签仍需单独指定 `--reuse-labels`。来源须有完整的规范断点和局面文件，基础搜索源码、Python、温度及搜索预算必须一致。完整历史和有效参数匹配才命中；来源条目损坏会报错，缺项则正常新算。优化器变化仍使训练断点失效，但相同实际搜索可以在新目录复用。旧棋谱记忆上下文、缺少身份的手工缓存或未完成来源不接受。最终串行计时在新实验内重新测量，不能把命中率当成棋力或算法速度收益。

另有 `gomoku.tools.pair_fit` 实验提案模块：针对已有候选中的同档错选，尝试生成能改变实际选点的叶子参数；仅由本地研究脚本调用，尚未接入训练 CLI 默认策略。

训练报告分别比较正式默认参数与本轮初始参数，记录质量、真实选点变化和计算成本。通过离线门槛不代表棋力提升；对照评测仍需固定对手、均衡开局及交换黑白。已经用于改进方案的验证集只作已见回归，保留测试不参与调参。详细表达式、缓存身份与优化策略见 [算法设计文档附录](算法设计文档.md#附录-d-新版分层离线训练)。
