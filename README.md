# 棋逢小鲸 v1.8.0

棋逢小鲸（Gomoku）是一个本地运行的五子棋程序，使用 15×15 棋盘，黑方先行，不设禁手。项目提供图形界面、命令行对战和 AI 自弈功能。正式版本采用纯 Python 算法，不需要联网，也不依赖大模型或神经网络。

## 快速上手

项目核心只使用 Python 标准库。安装 Python 3 后，在项目目录运行：

```bash
# 启动图形界面，推荐首次使用
python play.py

# 启动命令行对战，玩家执黑、AI 执白
python play_cli.py

# 让两个 AI 自动对弈，并把棋谱保存为 game.json
python -m gomoku.cli.vs_mode --max-moves 60 --out game.json
```

图形界面默认进入人机模式，玩家执黑。点击棋盘空位即可落子，AI 会在后台思考并自动应手。

命令行模式支持输入棋盘坐标，例如 `H8`；也可以输入零基行列坐标，例如 `7,7`。输入 `u` 悔棋，输入 `q` 退出。

终端里 AI 每走一手都会打印本次决策的来源（`棋谱开局` / `谱外开局规则` / `棋谱候选＋纯算法` / `纯算法`）、耗时、叶子评估状态和前五个候选（含五态）。开局谱着的分数显示为 `谱着`，不按必胜直取展示；这些字段都取自本次实际决策结果，命令行入口不另算一套。

# 第一部分：对弈界面与功能

## 1. 界面布局

图形界面分为三个区域：

- 左侧是控制区，用于选择对局模式、执子颜色和 AI 棋力，也可以新建对局、悔棋、认输、求和或查看记忆。
- 中间是信息区，用于显示双方落子、AI 思考时间、候选走法和判断结果。
- 右侧是棋盘。棋盘会随窗口大小自动缩放，最后一手棋会用红点标出。

AI 的计算在线程中进行，思考期间窗口仍可正常刷新。为避免状态混乱，AI 思考时不会接受新的棋盘操作。

## 2. 对局模式

### 人机

玩家可以选择执黑先行，也可以选择执白后行。轮到 AI 时，程序会自动计算并落子。

### 人人

黑白双方在同一台电脑上轮流落子，程序负责检查落点、胜负和对局状态。轮到任意一方时，
可以点击“AI辅助分析”让纯算法引擎分析当前局面；分析只在信息区列出首选点和前五个候选的
评分、五态结果，同时在棋盘上用由亮到暗的黄色编号光圈标出推荐顺序。它不会替玩家落子，
也不会改变棋盘；落子、悔棋或重开后，旧推荐会自动清除。
人机模式同样提供这个按钮，但只在轮到人类时可用——AI 回合的分析等于替 AI 想棋，按钮会置灰。
分析结果仅供玩家参考，不会改变 AI 的选点。
窗口最小尺寸为 900×560，保留控制面板、候选日志和棋盘的显示空间。

### 机机

图形界面中的“机机走一步”按钮每次让当前一方 AI 落一手，便于逐步观察计算过程。如果希望两个 AI 连续自动下完一局，可以使用快速上手中的 `vs_mode` 命令。

## 3. 对局操作

- **新对局**：按照当前模式和执子设置重新开始。
- **悔棋**：撤回最近的有效着法，并同步恢复棋盘、AI 内部状态和已经产生的终局结算。
- **认输**：当前应当操作的一方认输，立即结束对局。
- **求和**：将本局按和棋结束。
- **AI辅助分析**：人人模式双方都能用；人机模式在轮到人类时可用，AI 回合不可用（替 AI 分析没有意义）。后台分析当前行棋方的候选点，不自动落子，也不影响 AI 后续决策。
- **查看记忆**：查看累计战绩、输棋类型和历史棋谱信息。

## 4. AI 棋力

界面提供三个棋力档位。它们使用相同的判断方法，区别主要在于计算深度和用时：

| 档位 | 适合场景 | 特点 |
|---|---|---|
| 轻快 | 快速体验、简单局面 | 响应最快，计算较浅 |
| 标准 | 日常对弈 | 默认档位，兼顾速度和判断深度 |
| 认真 | 复杂中盘、算杀测试 | 计算更深，复杂局面可能等待较久 |

档位越高，AI 越愿意继续计算后续变化。实际用时由局面复杂程度决定，不是固定时间。

## 5. 思考结果

每次 AI 落子后，信息区会显示本次计算耗时和候选走法，通常列出前五个候选。每个候选可能包含：

- 棋盘坐标；
- 综合评分；
- 是否为最终选中的走法；
- 强制链状态：`必胜`、`存在必胜`、`无`、`存在必败`、`必败` 之一。

状态含义：

- `必胜` / `必败`：当前候选根节点的硬结论；
- `存在必胜`：尚未确定胜败，但对手有已知必败应手，可以利用对手的失误；
- `存在必败`：尚未确定胜败，但本方下一手有已知必败落点，需要避免自身失误；
- `无`：本次搜索尚未确定胜败，且没有上述本层证据。

软证据只在当前层有效，不再向父层传播；父层聚合时把 `存在必胜` / `存在必败` 当作“无”处理。

硬结论优先；两种软证据同时出现时显示“存在必败”。软状态不表示失误概率。界面不显示数值胜败比，所有结论均限于本次实际展开的搜索树，不代表全盘穷举证明。

“叶子评估：纯算法（N 个叶子）”表示 AI 本次实际评估了多少个搜索末端局面。“叶子未触发”表示这一步可以直接决定，例如立即成五、必须堵五或只有一个合法候选，不需要继续展开。

当前正式界面固定使用纯算法叶子评估和纯算法选点。项目中保留的网络接口属于实验或预留能力，默认关闭，也不属于正式发布内容。

## 6. 对局记忆

独立版默认把对局数据保存在：

```text
~/.gomoku/
├── games.json          进行中的对局
└── global-memory.json  总战绩、输棋类型和胜负棋谱
```

可以通过环境变量 `GOMOKU_HOME` 修改保存目录。对局结束后，程序会记录胜负和棋谱；如果终局后悔棋，原结算会一并撤销，重新结束时再重新记录。

# 第二部分：算法内部逻辑

## 1. 整体流程

AI 每次落子依次经过四个步骤：

```text
识别棋型 → 生成候选点 → 推演后续变化 → 排序并选择落点
```

对应的核心模块是：

```text
pattern → search → deep_search → engine
```

这四个模块共用同一套棋盘状态。图形界面、命令行和插件适配层只负责调用，不会另外实现一套选点规则。

## 2. 棋型识别

程序会检查棋盘上的每个空位，判断某一方落在这里后可能形成什么结构。判断时会观察横、竖和两个斜线方向，并把结果分为 18 个细分类别。为了便于理解，这些类别可以概括为：

| 类别 | 常见情况 | 作用 |
|---|---|---|
| 直接或强制取胜 | 成五、活四、双冲四、三四、双活三 | 优先寻找或防守 |
| 明显威胁 | 冲四、活三及其不同形态 | 用于连续进攻和逼迫应手 |
| 后续潜力 | 眠三、活二等 | 用于普通局面的候选评分 |
| 暂无作用 | 当前不能形成有效棋型 | 通常不会优先考虑 |

连续五子及以上按成五识别；连续段外隔着空位的同色棋子，不会把已经成五的结果降为带缝眠四。

黑白双方各有一张棋型状态表。真实落子和模拟落子后，程序只刷新受影响的区域，不必每次重新扫描整张棋盘：范围是**落子所在棋段**（以对方棋子或连续三空为界）的段内全部空缝，加上该棋段**两端外侧的空位**。这个范围与整盘重算逐格一致，所以既不需要额外的兜底区域，黑白双方也走完全相同的更新路径。

每个空位还按黑白分别缓存四个方向的档位。一次落子只重算区内各空位与落子共线的方向，其余方向直接复用，再合成原有棋型编号。模拟结束时，方向缓存和状态表通过同一份 journal 一起回滚；悔棋或载入棋盘时全量重建。这项优化减少重复扫描，不改变候选规则、评分、五态判定或搜索参数。

### 开局库（当前工作区已实现，尚未发布）

开局阶段按**本方已经落过几颗子**判断：本方第 1～3 次落子由开局模块选点，
不进入温度银行。命中完整盘面的棋谱就采用谱着，出谱则按邻接、连片和中心位置等
开局规则兜底；直接成五和必须堵五仍优先。执黑对应全盘第 1、3、5 手，执白为第 2、4、6 手。
每局从八种旋转/镜像视角中随机抽取一个，仅用于前三手接管；只会改变与当前完整盘面
对称等价的应手，不能随意旋转落点。同一局重复分析、实际落子和悔棋保持一致，新对局重新抽取。
黑方空盘首手仍为中心；局面打破对称后可能只有一个应手，因此不保证每局都走不同位置。

本方第 4 次落子起，命中的谱点只补入普通根候选，与原有候选一起深推。
已有强制攻防候选时不混入谱点；不修改递归宽度、原始权重计算或五态排序。
谱点已在候选中时不重复添加，否则至多增加一个根候选，可能增加该手计算量。
没有命中棋谱就沿原算法选点。谱着本身不产生必胜/必败标签，未展开时显示“无”。

开局数据来自 Rapfi 250615 的离线有限搜索，支持完整盘面及行棋方的八种旋转/镜像匹配；
不按输入着法顺序查谱，也不把局部形状或平移位置当成同一盘面。
当前数据由中心邻接变化生成，部分分支延伸至总第 12 手，覆盖不完整，不能视为最优着法证明。
正式运行只读取纯着法数据，不启动 Rapfi，不加载其模型，不新增第三方运行依赖。
数据来源、模型摘要和生成预算保存在 `gomoku/core/opening_book_data.py`。

需要更新数据时，可用 `scripts/generate_opening_book.py --engine <Rapfi可执行文件> --output-dir <临时目录>`
离线生成分析记录及待审查的数据模块。脚本不会下载或安装引擎，也不会自动替换正式开局库。
桌面辅助分析和实际落子显示“棋谱开局”“谱外开局规则”或“棋谱候选＋纯算法”，叶子统计仍按实际计算显示。

## 3. 候选点生成

程序不会从所有空位中盲目搜索，而是先按紧急程度筛选候选点：

1. 自己有一步成五的位置，直接取胜；
2. 对方下一步能够成五，优先封堵；
3. 自己存在活四、双冲四、三四等连续进攻机会，进入深度计算；
4. 对方存在上述威胁，生成相应防守点并保留不同防守点的重要程度；
5. 检查双方的双活三等强威胁；
6. 没有明确战术时，综合进攻与防守评分生成普通候选。

其中第 3 条里，四三（三四）在落子前会先确认一件事：对方被迫堵四的那一手，会不会顺手把自己的四也做成（反四）。会的话，这一步就不再按必杀处理，改由第 4 条及之后的判断决定。原因是四三要三步才能兑现（冲四逼应、活三转活四、补一端成五），只逼得动对手一手；对手那一手若同时成四，先手就换了人。活四、双冲四不受这条影响，它们一步堵不完。

普通局面下，程序会根据双方威胁强弱调整进攻和防守的比重。局面落后时更重视防守，局面占优时更重视进攻。历史棋谱也可以对普通候选分作小幅修正，但不会绕过当前局面的战术判断。

## 4. 深度推演

对每个根候选，程序会模拟“自己落一手、对方应一手”，然后继续向后计算。每次模拟落子都会同步更新棋盘和棋型状态；该分支结束后再完整恢复，保证不同候选之间不会互相污染。

深推使用“温度预算”控制计算量。可以把它理解为每一步拥有一笔有限的思考预算：

- 评分高、威胁大的走法消耗预算较少，因此可以继续看得更深；
- 普通或较弱的走法消耗预算较多，因此较早停止；
- 搜索越深，保留的候选会逐步减少，明显较弱的分支也会提前停止。

这种方式把更多时间放在关键攻防和连续杀棋上，同时避免普通局面的分支数量无限增长。界面中的“轻快、标准、认真”就是三种不同的初始预算。

深推先用硬状态筛选，再补齐根候选评分：对方已有必胜应手时，本方该分支可提前判败；同一方选择层找到必胜时，也不再为了判态继续展开其他选择。两种软状态和“无”不能用于硬剪枝。

先按原完整路径计算，直到找到一个非必败候选，再对后续候选启用硬态早停；全必败局面不额外先筛选一遍。所有非必败候选仍补齐原始加权分和直接子/孙节点证据；如果全部候选必败，则全部补齐原始分后选兜底。只有存在非必败替代时，已被淘汰且尚未完整评分的必败候选显示“未补算”（`score=null`、`score_complete=false`），不会拿中间累计分参与选择。其余候选 `score_complete=true`。补分复用本次已完整计算的子树和叶子，不从头重复计算；这些派生缓存只在本次固定上下文有效。

需要全部数值分的调用方可用 `analyze_turn(..., complete_scores=True)` 或 `rank_candidates(..., complete_scores=True)` 沿完整评分路径。可选网络和采样同样保留完整路径。Android 当前不显示候选分，独立界面与本地插件会显示“未补算”。每次决策固定入口温度，界面切档从下一手生效。温度仍按路径控制深度，不是新增节点总额度；本项没有引入跨回合派生状态缓存或全局节点上限。

## 5. 搜索末端评分

当某一分支已经分出胜负，或者思考预算耗尽时，程序会对当前结果评分：

- 已经成五时，胜方得到最高等级的结果；
- 尚未结束时，读取当前棋盘上双方每个空点可能形成的棋型；
- 先比较双方是否出现成五、强必杀（活四、双冲四、三四）、弱必杀（双三），出现即按固定分档计；
- 双方都没有必杀时，按全盘威胁分求和，再结合当前攻防倾向修正，最后做平滑压缩。

各分支的结果会按路径重要程度汇总。一路都选择高质量走法的变化影响更大，较弱或较深的变化影响会逐步减小。

这里的“评分”只用于比较候选好坏，不等同于“必胜”。高分候选仍可能没有得到明确的强制胜负结论。

## 6. 必胜、必败与五态判定

胜负状态与普通评分分别计算。实际成五直接提供确定的胜败证据，此前的布局或防守不会使终局证据失效；能否保证取胜，由每层双方的最优选择回传决定。

节点使用 5 个离散状态，硬结论与软证据分开保存：

```text
+1  必胜       硬结论
+2  存在必胜   软证据
 0  无         未确定且没有本层软证据
-2  存在必败   软证据
-1  必败       硬结论
```

每个落子节点描述该步落子方。直接子节点是对手的应手，孙节点是本方下一手：

- 对手有任一硬必胜应手 → 当前节点硬必败；
- 对手所有已展开的有效应手都硬必败 → 当前节点硬必胜；
- 未确定时，本方直接孙节点存在硬必败 → 存在必败；
- 否则，对方直接子节点存在硬必败 → 存在必胜；
- 其余为无。硬结论优先，软证据同时出现时风险优先。

存在必胜 / 存在必败只描述当前候选附近的失误机会或风险，不代表高手对弈下的确定结果。它们上传时按未确定保留分支，不翻转、不删除。风险只读取直接孙节点的硬败，不采集更深层任意败点。
直接成五候选可标必胜；堵五或其他唯一候选若未实际展开，只标无，不能从高分或唯一候选推断胜败。

这些结论只针对本次实际展开且没有被提前停止的变化，并不是对棋盘上所有可能走法的完整证明。

## 7. 最终选择顺序

所有根候选按状态档位排序，同一档内再比较候选分：

```text
必胜 > 存在必胜 > 无 > 存在必败 > 必败
```

- 只要存在更高档位的候选，就优先选择更高档位；
- 同一档位内按综合评分降序；
- 如果所有候选都落在败势档，先选“存在必败”里分数最高的，再轮到“必败”里分数最高的兜底；
- 如果所有候选都是“存在必败”，界面提示本方下一手均有失误风险，尚非确定必败；如果全部必败，则提示本次搜索中按候选分选择兜底。

## 8. 当前能力边界

- 开局和布局主要依靠局部棋型与攻防评分，对全局厚势和空间的理解有限；
- “必胜/存在必胜/存在必败/必败”都只来自本次有限搜索树，不是全盘穷举证明；
- 局面评分基于棋型分类，无法表达所有细微形状差异；
- 神经网络相关代码属于本地实验或预留能力，不代表当前正式版本正在使用网络。

### 与外部引擎对战（Gomocup / Piskvork 协议）

引擎可以按 Gomocup 的管道协议启动，从而接入 Gomocup 生态（和现成引擎对战、被管理器驱动）：

```bash
# 协议入口：从标准输入读命令、向标准输出回坐标
python -m gomoku.protocol

# 自建对战台：驱动两个协议引擎互相对局（支持均衡开局与黑白互换）
python -m gomoku.tools.match \
    --black "python -m gomoku.protocol --t0 40" \
    --white "path/to/pbrain-carbon.exe" --games 2 --swap --max-moves 120
```

- 坐标 0 基，协议里的 `(X, Y)` 对应内核 `(r, c) = (Y, X)`；
- `START` 只接受 15×15，其它尺寸回 `ERROR`（管理器可另试尺寸）；`START/BEGIN/INFO/BOARD/TURN/END/ABOUT` 均已实现；
- `BOARD` 接受乱序棋子，按双方子数确定黑白并交替重建盘面；有序输入保留原顺序，乱序输入无法恢复真实落子历史。非法坐标、重复点、不支持的 field 和不合法子数返回 `ERROR`；
- 每次输出立即 flush，且除协议内容外不向标准输出写任何东西（诊断走 stderr）；
- 可执行文件名必须以 `pbrain-` 开头才会被管理器按管道协议识别；
- `--t0` 用于覆盖推演温度：批量自对弈可降到 40 加速，正式对局保持默认 160。

已知限制：**没有迭代加深**，单手耗时由温度档位决定（T0=160 实测中盘 avg 3.08s、最慢 17.2s），
因此不能按 `INFO timeout_turn` 动态收缩预算；超时判定由管理器负责。

自建对战台按每方独立计时：初始化计入本方整局耗时，单步或整局任一正数时限超出即判负。
等待回复的预算取单步上限与本方整局剩余时间的较小值，持续输出 `DEBUG/MESSAGE` 不会重置计时；
超时后结束该局子进程。`START` 也有等待上限（正数单步时限，否则 30 秒，再受整局预算限制），
初始化失败单列为异常局；对战台未模拟 Piskvork 的初始化宽限与计时容差。

`python -m gomoku.tools.review --json <对战记录.json>` 可记录每回合的五态。
“存在必败”仍属非硬必败候选；实际着法不在候选时标为“未评估”，不据此认定败着。
只有实际着法已评估为硬必败且另有非必败候选时才报告该差异，结论仅针对本次搜索树，
“非必败”不保证可守，“全部候选必败”也不代表全盘已被穷举证明。

打包成管理器可识别的引擎（文件名必须以 `pbrain-` 开头，且**必须是控制台程序**）：

```bash
# 注意：--add-data 的相对路径是按 --specpath 解析的，必须给绝对路径
python -m PyInstaller --noconfirm --clean --onefile --console \
  --name "pbrain-QifengXiaojing" \
  --add-data "$(cygpath -w "$PWD/gomoku/data/ga_best_params.json");gomoku/data" \
  --exclude-module torch --exclude-module numpy --exclude-module gomoku.nn \
  --specpath build --workpath build/work --distpath dist \
  pbrain.py
```

Windows PowerShell 下等价写法：

```powershell
$ga = (Resolve-Path 'gomoku\data\ga_best_params.json').Path
python -m PyInstaller --noconfirm --clean --onefile --console `
  --name "pbrain-QifengXiaojing" --add-data "$ga;gomoku/data" `
  --exclude-module torch --exclude-module numpy --exclude-module gomoku.nn `
  --specpath build --workpath build/work --distpath dist pbrain.py
```

产物 `dist/pbrain-QifengXiaojing.exe` 可直接放进 Piskvork 管理器，或用上面的对战台驱动：

```bash
python -m gomoku.tools.match \
    --black "dist/pbrain-QifengXiaojing.exe" \
    --white "path/to/pbrain-carbon.exe" --openings 30 --parallel 4
```

批量模式会打印 A（`--black` 指定引擎）的胜率、Wilson 95% 置信区间与 Elo 差估计，
并可 `--json` 落盘——这是后续任何棋力改动的验收口径。

开局来源默认用**官方均衡开局集**（`gomoku/data/official_openings.json`）：Gomocup 官方管理器
Piskvork 的 `openings.txt` 共 41 条，其中 40 条适用于 15 路棋盘（1 条偏移超出棋盘，单独列出）。
锦标赛里由管理器自动摆前 3/5 手以保证同一对 AI 多盘不重样；用同一套开局做 A/B，我们的数字
才与 Gomocup 口径一致。需要时可 `--opening-set random` 切回随机开局（确定性种子）。

**棋力基线：重测中。** 此前记录的官方开局基线数字**已作废**——当时的对战台在启用自动开局时
只把最后一颗开局子用 `TURN` 发给引擎（正确做法是按 Piskvork 的实现发 `BOARD` 并附上全部石子），
导致引擎看不见前面的开局子、大量对局以"落子非法"提前结束（实测 40 局里 34 局如此）。
管理器已按 `source/protocol.cpp` 的写法修正，并新增回归用例
`test_game_with_official_opening_stays_legal`；三档（T0=40/160/240）的官方口径基线的重测结果
以 `gomoku/tools/match.py` 的 `--json` 输出为准，测完后回填本段。

### 运行测试

```bash
# 完整 Python 回归
python -m unittest discover -s gomoku/tests -v

# 深推、叶子与候选排序定向回归
python -m unittest gomoku.tests.test_leaf_value -v
python -m unittest gomoku.tests.test_deep_sync -v
python -m unittest gomoku.tests.test_rank_candidates -v

# 本地存在插件层和 Node.js 时运行
node --test gomoku/tests/test_plugin.cjs
```

### Android 客户端

`android/` 是 Kotlin + Compose 客户端，通过 Chaquopy 17 在 App 内运行同一套纯算法引擎；当前只产出 debug APK，release 需要配置签名。构建前先在仓库根目录同步内嵌引擎：

```bash
python scripts/sync_android_engine.py
python scripts/sync_android_engine.py --check
```

本地构建需要 JDK 17、Android SDK 和 Python 3.14，详细命令见 `android/README.md`。

### 发布产物

推送 `v*` 标签会触发 `.github/workflows/release.yml`：在 Windows EXE、Android debug APK、macOS zip 三平台全部构建成功后，才会创建并发布 GitHub Release，并附加 `SHA256SUMS.txt`。构建产物不进入源码仓库。

### 可选评估工具

| 工具 | 用途 |
|---|---|
| `gomoku/tools/eval_openings.py` | 用一组中盘局面批量评估不同设置 |
| `gomoku/tools/ga_tune.py` | 自动搜索棋型分值和搜索参数 |
| `gomoku/tools/bench_ga.py`、`verify_ga.py` | 对比并验证参数结果 |

自动调参结果默认不加载。如需启用已有的 GA 参数，可以设置环境变量 `DSH_GOMOKU_GA=1`。
